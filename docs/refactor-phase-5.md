## 재현한 문제와 수정

1. **저장 실패 뒤 성공 처리**: 등록·수정·삭제·총 발생일 변경이 메모리를 먼저 바꾸고 저장 실패에도 성공값을 반환했다. 실제 HTML에서도 입력 후 실패 시 메모리가 바뀌는 것을 재현했다. 이제 `commitVacationChanges`가 기존 중앙 `commitLocal`·미전송 경로로 후보를 저장·재확인한 다음 반영한다. 폼과 삭제 이벤트는 실패 시 입력·기존 목록을 유지하고 성공 안내를 내보내지 않는다.
2. **발생 연차 0일**: 저장값 0이 통계와 입력창에서 15로 해석됐다. 유효한 0과 값 부재를 구분했다. `setTotalVacationDays`는 성공 시 숫자(0 포함), 실패 시 `null`을 반환하며 호출부도 `null`을 검사한다. 빈 값·음수·유한하지 않은 입력은 기존 값을 바꾸지 않는다.
3. **0일 차감 휴가의 잘못된 표시**: 챗봇이 휴가 0을 1일로 차감했고, 달력 칩·날짜 상세는 휴가를 오후 반차로 표시했다. 챗봇은 Store 통계를 사용하고, 통계·기간 요약·달력 합계는 `getVacationAmount`로 같은 차감량을 읽는다. 휴가 칩·날짜 상세는 0일로 표시한다. 기존 연차 원본을 수정하는 계산은 아니다.
4. **다음 연도 선택 누락**: 자료 없는 2027년처럼 현재 연도가 기존 2025/2026 선택지에 없는 조건을 검사했다. 현재 연도와 현재 선택 연도를 선택지에 포함한다. 기존 여러 연도 기록, 전체 기간 휴가 필터와 정렬 정책은 유지한다.
5. **삭제된 연차의 재유입**: 삭제가 이미 동기화된 뒤 오래된 서버 기록을 받거나, 삭제 기록과 동일한 오래된 행이 양쪽에 남는 상황을 재현했다. 4차의 사이트 보호와 같은 중앙 병합 조건에 `vacations`만 추가했다. 서로 다른 수정은 충돌 원문과 로컬 미전송 변경을 보존한다. 서버 내용을 임의로 덮어쓰며 충돌을 해소하지 않는다.
6. **관련 없는 기존 할 일 변경**: 분류가 없거나 오래된 분류를 가진 할 일을 읽을 때 초기화용 보정이 파싱 원본 객체까지 바꿨다. 연차 저장이 그 변경까지 저장하는 문제가 실제 HTML 검사에서 드러났다. 임시 할 일 배열을 깊이 복제해 최종 원본 복원을 보장했다.
7. **관련 없는 삭제 폴더 재생성**: 같은 참조 공유 문제로 건강·취미·파일보관함의 비어 있는 폴더 목록이나 사용자 폴더만 남긴 목록에 기본 폴더가 다시 들어갔다. 합성 자료로 재현한 뒤 이 세 임시 배열만 복제했다. 사용자 목록 필드 자체가 없는 구버전 자료의 기본값 지원은 유지한다. 첨부파일 원문이나 해당 기능의 저장·삭제 구현은 변경하지 않았다.

6·7번은 연차 편집이 다른 자료를 변경하지 않는다는 합격 조건 때문에 포함한 추가 보완이다. 폴더 보완은 화면 이동과 별도 커밋으로 남겼다.

## 유지한 정책과 한계

- 총 발생 연차는 기존의 단일 숫자다. 상단 사용량은 전체 기록 합계이고 기간 요약은 선택 연도/월을 따른다. 별도 휴가 필터는 전체 기간의 휴가를 보여준다. 연도별 발생 연차·이월 정책이나 기존 2026 안내 문구 전체의 재설계는 이번 범위에 포함하지 않았다.
- 실제 사용자 프로필, 개인 복구 파일, 운영 Firebase, IndexedDB 첨부파일 원문은 열거나 수정하지 않았다. 테스트의 외부 요청은 가로채거나 차단하며 CDN PDF/Excel 기능 자체는 검증 범위가 아니다.
- 가상 기기의 검사 통과는 모든 실제 기기·구버전 코드의 무손실 보장이 아니다. 구버전에는 같은 보호 처리가 없을 수 있고, 기존 충돌의 자동 해결 기능을 새로 만들지는 않았다.
- Git 커밋은 소스 복구 지점이다. 실제 운영 적용 전에는 개인 데이터·첨부파일·기기별 은행 자료의 별도 백업과 복원 범위를 확인한다.

## 중단·복구

자료 손실, 다른 자료 변경, 실패 후 성공 안내, 불필요한 저장, 중복 이벤트 또는 충돌 원문 손실이 발견되면 다음 작업을 중단하고 재현한다. 화면 분리만 되돌릴 때는 목록 → 총 발생일 모달 → 등록/수정 모달의 역순으로 해당 커밋을 되돌려 안전성 수정은 유지한다. 두 HTML의 로딩 순서와 테스트의 팩토리 로딩도 함께 복구한다.

안전성 수정 이전 코드로 돌아가면 기존 문제가 다시 생길 수 있다. 강제 reset, 데이터 초기화, 개인 복구 파일 덮어쓰기, 오래된 서버 데이터의 강제 업로드는 복구 방법에 포함하지 않는다.
