# 중앙 동기화 진단·분리·변경 항목 전송

## 기준과 단계

- 시작점은 실제 웹·모바일에서 양방향 동기화와 완료 상태 유지를 확인한 `43db260`이다. 6차 취미·7차 건강 화면의 분리 파일을 유지한다.
- `dd7128d`: 최근 60건의 진단 기록을 기기에 보관하고 설정에서 JSON으로 내보낸다. 시각·단계·상태 코드·시도 횟수·처리 시간·전송 크기만 허용한다. 본문, URL, 계정, PIN, 임의 오류 메시지는 저장하지 않는다. 기록 저장 실패는 업무 데이터 저장을 막지 않는다.
- `749c615`: 병합/미전송 규칙을 `js/sync/protocol.js`, 중앙 실행기를 `js/sync/manager.js`로 이동했다. 기존 Store/UI/Vault를 getter로 연결하며 다른 Store나 타이머를 만들지 않았다. 이동 직전 코드와 본문이 동일함을 의존성 연결 치환 후 비교했다. 328개 Node 검사와 실제 두 HTML의 기존 암호화 동기화·원문 복구 검사를 통과했다.
- 세 번째 단계는 `js/sync/object-transport.js`다. 중앙 병합·미전송·원문 보관·PC 가계부 우선 규칙은 그대로 사용하고 전송 표현만 변경한다.

## 전송 순서

1. 기존 `/spaces/<account>.json`을 ETag와 함께 읽는다. v2/v3 및 이전 평문은 기존 규칙으로 읽고, v4는 암호화된 최신 목록을 읽는다.
2. 큰 `data:` 첨부와 개별 기록을 기존 AES-GCM/PBKDF2 엔진으로 각각 암호화한다. 10MB 문자열 제한을 피하는 기존 v3 조각 표현도 계속 사용한다. 목록 순서는 별도 기록이며 삭제 표식·항목별 수정 버전·PC 가계부 출처도 유지한다.
3. `/sync_objects/<account>/<id>.json`에 `if-match: null_etag`로 새 객체만 저장한다. ID는 별도 목적의 PBKDF2/HMAC-SHA256으로 계정 범위와 내용 해시에서 만든다. 평문 내용 해시는 암호화된 최신 목록 안에만 둔다. 같은 원문은 같은 ID를 사용하며 기존 객체를 덮어쓰거나 자동 삭제하지 않는다.
4. 객체가 이미 있거나 응답이 유실된 경우, 기존 암호문을 읽어 복호화·내용 해시를 확인한다. 누락·변형·형식 오류를 빈 자료로 해석하지 않는다.
5. 모든 객체 저장 확인 후 작은 v4 최신 목록을 원래 ETag 조건으로 교체한다. 다른 기기가 먼저 저장하면 412를 받고 다시 읽고 병합한다. 객체만 일부 저장된 상태에서는 기존 최신 목록이 유효하다. 사용 중인 PIN·계정·로컬 원문·첨부 쓰기 상태가 바뀌면 오래된 목록을 완료 처리하지 않는다.
6. 서버의 최신 목록 저장과 기기의 원문 저장을 확인한 뒤에만 미전송 기록을 해제한다. SSE는 계속 작은 `iv`만 구독한다.

Firebase의 조건부 저장은 [공식 REST 문서](https://firebase.google.com/docs/database/rest/save-data#section-conditional-requests), 빈 위치에만 생성하는 `null_etag`는 [REST API 참조](https://firebase.google.com/docs/reference/rest/database)에 따른다.

### 요청 옵션 호환 수정

최초 v4 배포에서 기존 최신 목록 전송에만 있던 HTTP 400 응답 옵션 복구 처리가 기록·첨부·기존 암호문 백업 경로에 빠졌다. 운영 서버는 v3에 머물고 새 객체는 0건인 상태에서 양쪽 기기가 실패를 보고했다. 응답 옵션 거절 모형에서 수정 전 실패를 재현하고, 모든 조건부 쓰기를 중앙 `conditionalPut()`으로 통합했다. 400이면 크기 제한을 제외하고 `print=silent`만 제거해 한 번 재시도한다. 암호문·ETag는 유지하며, 새 입력·계정 변경 시 오래된 재시도는 완료 처리하지 않는다. 동기화 실패의 상세 문구는 3초 자동 숨김 대상에서 제외했다. 실제 오류 응답 본문은 기기 연결 부재로 직접 확보하지 못했으므로, 운영 증상의 해결은 배포 후 두 기기 및 서버 상태로 추가 확인한다.

## 원문과 구버전

- 최초 형식 전환 전에 기존 서버의 암호문 전체를 별도 불변 객체로 보관하고, 암호화된 최신 목록의 `legacySnapshot`이 그 위치와 해시를 가리킨다. 기존 기기 원문·충돌 원문 보관도 유지한다. Git 복구 지점과 개인 데이터 백업은 별개다.
- v4의 최상위 `payload`는 문자열이 아닌 객체다. 구버전 복호화기는 이를 거부하므로 불완전한 목록을 업무 데이터로 오해해 재전송하지 않는다. 이미 열린 구버전 웹·모바일 화면은 새로고침이 필요하다. 전환 중 기존 미전송 기록은 지우지 않으며 새 코드로 다시 열면 병합에 참여한다.
- v4 전환 후 이전 코드만 재배포하는 방식으로 롤백하지 않는다. v4를 읽을 수 있는 코드를 유지한 채 수정한다. 원문 복원은 새 기록까지 포함한 보호 백업을 확인한 별도 절차다.
- 최초 전환과 새 기기의 최초 수신에는 전체 원문 전송이 필요하다. 이후에는 바뀐 기록·첨부와 작은 최신 목록만 전송한다. 재시작 시에도 기기에 저장된 원문 해시가 같으면 같은 첨부를 다시 받지 않는다.
- 객체 메모리 캐시는 최대 128개/약 32MiB이며 업무 데이터의 기준이 아니다. 병합용 큰 기록의 해시 캐시도 크기를 제한하고 내용 전체가 같은 경우에만 사용한다. 로컬 IndexedDB 저장 형식은 변경하지 않았다.
- 이 단계는 오래된 객체를 정리하지 않는다. 자동 정리는 보관 원문·미전송·다른 기기 상태와 복원 검사를 포함한 후속 작업이다.

## 검증

- `node --test tests/*.test.cjs`: 기존 회귀와 진단·객체 전송 검사를 포함한 347개 검사를 통과했다.
- `node tests/object-sync-ui.cjs`: 실제 두 HTML, PC 2대/모바일, IndexedDB, AES-GCM, HTTP/SSE로 23MB 이상 자료의 전체 항목·첨부 일치, 일정 추가, 503 재시도, 삭제, 재실행, 무변경 상태의 반복 전송 없음, 진단 파일 다운로드를 검사한다.
- `SYNC_REJECT_PRINT=1`을 설정한 같은 브라우저 검사에서는 응답 옵션 거절 400 → 동일 조건의 일반 PUT 200 응답 → 원문 일치·재실행까지 검증한다.
- `node tests/automatic-sync-ui.cjs`: v4의 PC 가계부 우선, 양쪽 원문 보관, 메모/건강 첨부, 실제 저장 용량 부족, 복구 파일 내보내기, 두 HTML과 `file://`를 검사한다.
- `node tests/full-sync-ui.cjs`: 명시적으로 v3를 유지한 구형 스냅샷 호환 검사다. 기능별 과거 UI 서버 모형도 이 호환 경로를 사용한다. v4를 받은 뒤 v3로 되돌리는 옵션은 아니다.
- 객체 저장 실패, 최신 목록 저장 실패·응답 유실, 전송 중 새 입력, 동시 수정 412, 객체 누락·변형, 구버전 중단 후 업데이트·미전송 재전송을 검사한다.
- 최종 가상 23MB 브라우저 검사에서 일정 한 건 업로드는 34,763바이트, 세 기기의 합산 다운로드는 102,671바이트였다. 두 HTML에서 SSE 반영 시간은 약 1.45/1.59초였다. 실제 모바일 통신의 2초 보장은 아니다.
- 프로파일 확인 시 `PROFILE_SYNC=1`, `SYNC_ENTRY_ONLY=index.html`을 설정하고 `object-sync-ui.cjs`를 실행한다. 프로파일의 비동기 구간 시간은 서로 겹치므로 합산하지 않는다.

## 배포 확인

코드·가상 기기 검증과 운영 데이터의 형식 전환은 구분한다. 배포 커밋의 Pages 성공 및 실제 JS 일치를 확인한 다음, 사용 중인 두 기기가 새 코드를 읽었는지와 실제 양방향 반영을 확인한다. 에이전트의 기존 PIN 재사용 승인은 읽기 전용 진단이며, 복구 스크립트로 운영 데이터를 직접 다시 쓰는 권한이 아니다.
