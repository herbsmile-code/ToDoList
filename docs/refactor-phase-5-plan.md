# 5차 계획: 연차관리 안전성 확인과 화면 분리

상태: 사용자 승인 후 5차 안전성 수정과 화면 분리를 구현했다. 아래는 실행 전 계획이며, 최종 변경·검증·복구 기준은 [5차 결과](refactor-phase-5.md)에 기록한다. 운영 자료 접근·main 병합·배포는 하지 않았다.

## 목적과 시작 기준

연차 내역, 사유, 날짜, 차감 일수와 미전송 변경을 보존하면서 연차 화면 코드를 찾기 쉽게 분리한다. 4차 검토 완료 태그 `codex/phase-4-reviewed-20260919`를 시작 기준으로 삼고, 구현 승인을 받은 뒤 별도 `codex/refactor-phase-5` 브랜치에서 진행한다.

기존 자료의 저장 키·ID·자료 형식·암호화 형식은 유지한다. 연도별 발생 연차 모델을 새로 만들거나 기존 기록을 일괄 변환하지 않는다. 실제 사용자 프로필·복구 파일·운영 Firebase를 테스트 입력으로 사용하지 않는다.

## 확인한 연결 구조

- Store의 `addVacation`, `updateVacation`, `deleteVacation`, `setTotalVacationDays`가 변경을 처리하고 `getVacationStats`가 합계를 계산한다.
- UI의 `renderVacation`, `openVacationModal`, `closeVacationModal`, `openTotalVacationModal`, `closeTotalVacationModal` 5개가 분리 대상이다.
- 월별 달력과 선택한 날짜 화면도 `store.vacations`를 읽는다. 할 일의 `type: vacation/half-off`는 별도 기록이므로 자동으로 합치거나 이중 차감하지 않는다.
- 챗봇의 남은 연차 표시, 연도·월 필터, 상단 통계 클릭, PC/모바일 메뉴, 입력 폼과 삭제 이벤트가 연결돼 있다.
- 현재 총 발생 연차는 단일 숫자다. 상단 사용량은 전체 기록을 합산하고, 기간 요약은 선택 연도·월을 따른다. 별도 휴가 필터는 기존 요구대로 전체 기간의 0일 차감 휴가를 표시한다. 화면 분리를 이유로 이 정책을 변경하지 않는다.

## 사전 재현 및 추가 확인 대상

| 항목 | 현재 확인 수준 | 5차 대응 |
|---|---|---|
| 총 발생 연차 0일 | 합성 저장 자료의 값은 0인데 `getVacationStats().total`은 15로 계산됨을 재현 | 0과 값 부재를 구분. 총 연차 입력창·챗봇도 함께 검사 |
| 로컬 저장 실패 | 생성·수정·삭제·총 발생일 변경 4경로 모두 저장 실패 후 메모리를 변경하고 성공으로 해석될 값을 반환함을 합성 자료로 재현. 저장 원본은 유지됨 | 저장 확인 후 메모리 반영, 실패 시 입력·기존 목록·미전송 기록 보존. 총 발생일 0을 실패값으로 오인하지 않는 반환 규칙 사용 |
| 실패 후 성공 안내 | 폼·삭제 이벤트가 저장 결과를 검사하지 않는 코드 확인 | 실제 HTML에서 실패를 재현하고, 실패 시 모달 유지·성공 안내 및 후속 화면 변경 차단 |
| 챗봇의 0일 차감 휴가 | `amount || 1.0`으로 계산하는 코드 확인 | 휴가 0·반차 0.5·연차 1과 화면 계산을 대조. 잘못된 표시가 재현되면 별도 수정 커밋 |
| 연도 전환 | 기본 선택은 현재 연도이나 선택지에는 2025/2026 고정 초기값이 있음 | 미래 연도·해당 연도 기록 없음·전체 연도 조건을 검사. 기록을 만들거나 변경하지 않고 선택과 표시 일치 확인 |
| 기기 간 수정·삭제 충돌 | 연차 전용 검사 부족 | 같은 기록 동시 수정, 삭제 대 수정, 총 발생일 충돌, 오래된 서버 재수신에서 양쪽 원문과 미전송 변경 보존 검사 |

재현에서 사용한 합성 자료와 로그는 `scratch/phase4-review.cjs` 등이며 개인 자료를 사용하지 않았다. 위 문제의 수정은 5차 구현 시작 이후에 진행한다.

## 작업 순서와 커밋 경계

1. **기준 검사 확보**
   - `tests/vacation-safety.test.cjs`, `tests/vacation-ui.cjs`를 작성한다.
   - 두 HTML, PC/모바일, 밝은/어두운 테마, `file://`에서 기존 정상 동작을 기록한다.
   - 연차 1일, 오전/오후 반차 0.5일, 별도 휴가 0일, 발생 0일, 빈 기록, 여러 연도, 수정·삭제, 날짜 정렬과 필터를 검사한다.
   - 알려진 실패를 재현한 결과와 원래 정상인 동작을 구분해 둔다.
2. **저장·계산 안전성 보완**
   - 단일 Store 안에서 기존 `commitLocal`·미전송 기록·중앙 동기화 경로를 재사용한다. 별도 연차 저장소·클라우드 업로드·타이머는 만들지 않는다.
   - 변경 후보 저장과 재확인이 성공한 뒤 화면에 반영한다. 삭제 내역과 삭제 기록도 한 후보로 저장한다.
   - 0 처리와 실패 처리 등 재현된 결함만 수정한다. 연도별 발생 연차 정책이나 자료 변환이 필요해지면 별도 설계 대상으로 보고한다.
   - 안전성 변경과 파일 이동은 별도 커밋으로 남긴다. 의도적으로 수정한 동작을 명시하고 이후 화면 비교 기준을 확보한다.
3. **등록·수정 모달 분리**
   - `js/features/vacation/view.js`에 `createVacationView` 팩토리를 만들고 열기·닫기 2개 함수를 옮긴다.
   - 기존 Store·날짜 함수 등을 전달하고 `UI`에 합성한다. 저장·공통 이벤트는 `app.js`에 둔다.
4. **총 발생 연차 모달 분리**
   - 열기·닫기 2개 함수를 옮기고 0일 재표시, 취소, 반복 열기, 저장 실패 시 입력 보존을 확인한다.
5. **목록·통계 화면 분리**
   - `renderVacation`을 옮기고 목록·필터·통계·날짜 정렬·빈 화면을 기존 기준과 비교한다.
   - 화면 표시만으로 저장·동기화가 발생하거나 원본 배열·값이 변경되지 않아야 한다.
6. **통합 검증과 복구 지점**
   - 두 HTML의 로딩 순서·캐시 식별자를 맞추고 달력·모바일 메뉴·챗봇 등 연결 화면을 검사한다.
   - 기존 저장·동기화·AI·사이트·가계부 관련 회귀 검사를 변경 영향에 맞게 실행한다.
   - 결과와 복구 방법을 기록하고 별도 검증 커밋을 남긴다. GitHub 게시·main 병합·운영 배포는 각각 승인된 범위에서 수행한다.

## 자료 보존 합격 조건

- 연차 변경에서 메모·사이트·가계부·사진 등 관련 없는 저장 필드가 그대로 유지된다.
- 읽기 실패·저장 공간 부족·저장 후 재확인 실패·다른 창의 편집에서 기존 원본을 초기화하지 않는다.
- 업로드 실패 → 앱 재실행 → 오래된 서버 수신 → 재전송에도 미전송 연차와 원문이 유지된다.
- 삭제 충돌·동시 수정은 원문을 보존하며, 단순 수신을 충돌 해결 또는 전체 동기화 완료로 표시하지 않는다.
- 모달 열기·닫기·필터 변경·화면 재표시만으로 자료가 재저장·재생성되지 않는다.
- 두 진입 HTML, PC/모바일, 로컬 HTML 실행에서 같은 저장·표시 결과를 보인다.
- 실제 운영 적용 전에는 소스 백업과 개인 데이터 백업을 구분하고, 첨부파일·기기별 자료를 포함한 복구 범위를 확인한다. 검사용 합성 데이터의 통과를 실제 자료 백업 완료로 보고하지 않는다.

## 중단과 복구

원문 손실, 다른 기능 자료 변경, 실패 후 성공 안내, 불필요한 저장, 삭제 기록의 부활, 중복 이벤트가 발생하면 다음 분리 단계로 넘어가지 않는다. 화면 분리 문제는 해당 분리 커밋만 되돌려 이미 검증한 안전성 수정을 유지한다. 초기화·강제 reset·force push·오래된 클라우드 덮어쓰기는 복구 수단으로 사용하지 않는다.

5차 완료 기준은 파일 크기 감소가 아니라, 기존 자료를 보존하면서 연차 화면의 책임과 관련 검증이 독립적으로 이해 가능한 상태다.
